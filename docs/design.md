# 技术方案

本文是 Best Post Manager 的实现边界。它服务于一个人的本地工作流：保存自己的内容，按平台制作版本，并记录发布结果。方案优先支持可恢复、可解释的本地操作，不把平台差异藏在一个“万能爬虫”里。

## 目标与原则

- **本地优先**：应用、数据库、图片和凭据都由用户控制；断网时仍可编辑已有内容。
- **单用户**：Profile 是内容身份/语气分组，不是账户权限。永远不设计多人、组织、RBAC、审核协作或云同步。
- **显式操作**：发布和外部导入都是用户发起的；URL 关联不触发后台抓取，不猜测远端可见性。
- **平台诚实**：每个 adapter 声明能力和限制。无法可靠自动化的平台使用浏览器桥接，并保留人工确认。
- **内容可追溯**：基础稿、平台版本、媒体和发布记录相互关联；失败不抹掉可重试的输入。
- **小而可替换**：应用层定义少量领域接口，具体 API 客户端、翻译服务和桥接脚本可以替换。

## 总体架构

首阶段采用 Go 单体：HTTP API、应用服务、存储和平台 adapter 在一个进程中，Vue 3 + TypeScript SPA 由 Go 嵌入并提供静态资源。SQLite 保存结构化数据，本地媒体目录保存原始文件和派生预览。CLI 调用同一应用服务，不另写一套业务规则。

```text
Vue SPA ─┐
CLI     ├─> Application services ─> repositories / media store / adapters
Browser ┘                         ├─> SQLite
                                  └─> local media directory
```

WebUI 与 CLI 都是本地入口。HTTP API 只监听本地回环地址；若未来确实要改变暴露方式，必须另做认证和威胁模型，不应由首版默认开放局域网。

## 领域模型

以下是指导实现的边界，不要求一开始为每个概念建过度通用的框架。

- **Profile**：内容身份分组，例如个人或项目品牌。包含名称、默认语言和可选描述。一个 Profile 可以拥有多个平台、多个账号。
- **Account**：某个平台的一个账号连接，且必须且只能属于一个 Profile。一个平台可在同一 Profile 下有多个 Account；保存平台类型、显示名称、远端身份和凭据引用，不把令牌放入正文或日志。不设计共享 Account，也不允许 Account 跨 Profile 复用。
- **Topic**：一个跨平台话题/创作单元，包含标题、状态和关联的 BaseDraft、Variant、Publication、ExternalPost。
- **BaseDraft**：与平台无关的主文稿，可含文字、结构化媒体引用、语言和编辑元数据。它是版本生成的来源，不代表已发布内容。
- **Variant**：Topic 在某个平台/Account 上的实际版本，保存正文格式、平台选项、媒体顺序、语言和来源。首次从 BaseDraft 生成的平台版本为 **linked**，并记录生成时的 BaseDraft revision；从其他 Variant 复制的版本默认是 **detached**。
- **Publication**：一次对某个 Account 的发布尝试及结果。成功时记录远端 ID/URL 和时间；失败时保留错误类别、可重试性及请求幂等键。
- **ExternalPost**：用户在本程序外发布的帖子关联。它可以只有 URL/远端 ID，也可以有由浏览器或官方 API 得到的本地内容快照。
- **Media**：本地媒体元数据（文件、MIME、尺寸、替代文本、校验值）及其在稿件中的顺序。平台上传后的远端媒体 ID 属于对应发布结果，不替代本地源文件。

### 版本关系与状态

Variant 与 BaseDraft 的关系遵循一个简单规则：首次生成是 **linked**，记录源 revision；BaseDraft 变化时，系统只把 linked Variant 标记为 `outdated`/“有更新”，绝不静默覆盖平台版本。用户必须主动选择“应用更新”或重新生成，确认后才把当前 BaseDraft 内容应用到该 Variant，并更新其源 revision。用户第一次直接编辑平台 Variant 时自动转为 **detached**（界面应明确提示），之后 BaseDraft 更新不再标记或覆盖它；从其他 Variant 复制也始终是 detached。这样保留来源追踪而不引入实时同步或复杂冲突合并。

三种实体使用各自的最小状态，不共享一个状态枚举：

- **Topic**：`active`、`archived`。新建时为 active；归档只影响工作列表，不删除其版本和历史。
- **Variant**：`draft`、`ready`。`linked`/`detached` 是与 BaseDraft 的关系，不是状态；linked 的源 revision 落后于 BaseDraft 当前 revision 时派生显示 `outdated`，用户主动应用更新后清除。detached 永远不会因源稿变化被标记或覆盖。
- **Publication**：`pending`、`publishing`、`published`、`failed`、`needs_confirmation`。网络超时或桥接结果不明时使用 `needs_confirmation`（结果未知/待确认），不能当作失败或未发布；用户检查平台后可补录远端结果。外部关联的来源另以 `source=internal|external` 等来源信息记录，不改变发布状态。

`publishing` 在程序重启后必须能恢复为可检查状态；失败不能伪装成未尝试。

## 存储与应用 API 边界

SQLite 表按上述实体拆分，使用稳定的本地 ID、创建/更新时间和必要的外键；正文和平台选项可以先用 JSON 文本存储，但应用层要校验版本化结构。删除采用软删除或明确的级联策略，不能因删除一个 Topic 误删用户媒体。

首阶段 API 只需覆盖：Profile/Account 的增删改查，Topic 与 BaseDraft 编辑，Variant 创建/复制、linked 的 source revision/outdated 状态、用户确认的应用更新和 detached 编辑，Media 导入，Publication 预览/发布/重试/标记外部结果，以及 ExternalPost 的 URL 标记和浏览器快照接收。API 应返回能力校验错误和用户可行动的提示；不要暴露任意数据库查询。

## Profile、账号与凭据

Profile 仅做内容分组；Account 负责平台连接。一个 Account 只能指向一个平台身份，且只能归属一个 Profile；同一 Profile 可有多个平台和多个 Account，同一平台也可有多个 Account。不设计共享 Account。删除或停用 Account 不得删除历史 Publication。

凭据通过本地凭据存储或操作系统 keychain 保存，SQLite 只保存引用和非敏感元数据。token 不出现在 API 响应、CLI 普通输出、错误消息或日志中。用户主动导出数据时默认排除凭据，导入时明确提示可能含敏感内容。

## 平台能力与 adapter

应用层面向一个小的发布接口：校验 Variant、生成平台请求、上传所需媒体、提交、规范化远端结果。每个 adapter 另提供 capability 描述（字符/字节限制、内容格式、emoji 规则、媒体类型/数量、可见性、内容警告），预览和首版表单据此工作。平台特有选项保存在 Variant 的平台选项中，未知选项不能静默丢弃。

### Fediverse

- **Mastodon-compatible**：使用实例提供的标准 API，配置实例 URL、令牌、可见性、内容警告和媒体上传；首节点在账号设置或用户主动刷新时获取实例 custom emoji，按实例 URL 缓存其短代码与图片信息，在预览中渲染；发布仍发送平台原生短代码/规则，缓存不可用时回退为短代码。实例能力差异以运行时错误呈现，不做后台轮询刷新。
- **Misskey**：使用 `{instance}/api` 官方 POST API：图片先走 `drive/files/create`，再用 `notes/create` 发布；支持 MFM（至少保存原始 MFM，不把 Markdown 假装成 MFM）、note 可见性、CW、localOnly 和自定义 emoji。emoji 按实例缓存；新版本 entity 缺少 URL 时按实例 `/emoji/{escaped-name}.webp` 派生。保留原生短代码/规则发送。MFM 预览需要明确标记其渲染器，避免误发 HTML。
- Misskey 的 `notes/create` 没有可依赖的幂等键；本地 key 只用于记录，不能伪装成远端幂等。最终提交超时或 5xx 进入待确认，不能盲目重试。

两者都只发布用户选定的 Variant，不抓取关注时间线，也不默认扫描账号最近帖子。URL 导入若没有官方可用的单帖查询，则保持 URL 标记模式。

### Bluesky

使用官方 AT Protocol XRPC：`com.atproto.server.createSession` 建立内存会话，`repo.uploadBlob` 上传图片，`repo.createRecord` 创建 `app.bsky.feed.post`；`resolveHandle`/`repo.getRecord` 使用 GET 查询。处理链接/提及的 UTF-8 byteStart/byteEnd facets 和图片 blob。远端记录 key/URI/CID 等标识，发布前完成 3000-byte record 与图片限制校验。`createRecord` 不提供本地可复用的幂等键，最终提交未知时保持待确认。首版只做明确的发帖/单帖导入能力，不做时间线同步。

## 浏览器桥接

X、微博、小红书和 QQ 空间无法依赖稳定的公开发布 API 时，使用用户主动安装的浏览器用户脚本。脚本是平台适配器，不是服务端爬虫；它在用户已经登录、当前可见的页面读取 DOM，将结构化消息发到本地桥接端点。

### 协议

桥接协议应有版本号、一次性配对码/短期 token、请求 ID 和消息类型，至少包括 `hello`、`fill`、`capture`、`result`、`error`。消息包含平台、页面 URL、可选远端 ID、文本/媒体描述、可见性和用户确认所需的提示。请求大小、媒体数量和来源 URL 要有限制；所有消息在本地回环端点校验来源和 token。

本地端点默认只接受一次配对后短期有效的请求，并拒绝任意跨域调用。token 不写入网页内容、URL 或普通日志。脚本应显示连接状态和实际发送的数据摘要，让用户能撤销配对。桥接端点只服务当前本地用户，不是通用远程 API。

### 导入和发布边界

导入只读取页面当前可见 DOM 及用户主动展开的内容。私密帖子依赖用户在浏览器中的既有权限；程序不绕过登录、验证码、付费墙、权限检查或反爬机制，不调用隐藏接口来扩大可见范围。无法读取的内容标记为不完整，由用户补充。

发布时默认把 Variant 填入平台编辑框，随后由用户在页面检查并人工点击最终发布。脚本可回传用户确认后的远端 URL/ID，但不应在没有明确确认的情况下自动点击发布。QQ 空间的可见范围、说说格式和图片顺序属于平台选项；脚本无法可靠设置时必须提示用户检查当前页面选择。

## 站外帖子与快照

ExternalPost 有两种有意不同的模式：

1. **URL 标记**：保存平台、Account（若已知）、URL/远端 ID、时间、可见性（若用户提供）和备注。此操作零网络抓取，用于表示已发布。
2. **内容快照**：通过浏览器桥接或官方单帖 API，由用户请求后保存正文、媒体描述、格式、作者/时间和捕获方式。快照是当时内容的本地副本，原帖删除或变私密后仍可用于复用。

媒体只在浏览器脚本确实有权读取并成功传回时本地化；跨域或权限阻止读取时保存元数据并提示手动添加。快照不会定时刷新，也不会因打开 Topic 触发远端请求。

## 内容格式、emoji、媒体与预览

内容内部保存原始文本、声明格式和结构化媒体引用。Markdown、MFM 和平台纯文本不可互相冒充：转换必须是显式的，无法表达的语法在发布前给出警告。平台 emoji 可保存短代码与可选图片引用；预览使用对应渲染器或降级为清楚标注的文本。

媒体先进入本地存储，计算校验值并记录 MIME/尺寸/替代文本。首版发布前只由 adapter 校验并报告平台的大小、数量和格式限制，不自动裁剪、压缩或转码；只允许生成用于 WebUI 预览的本地缩略图。预览不应为了显示而偷偷从远端下载受保护媒体。自动媒体处理属于 Backlog。

## 翻译 provider

翻译是显式的应用操作：用户选择源语言、目标语言、provider 和要翻译的 Variant/文本范围，结果创建新的 Variant 或草稿，不覆盖原文。Provider 接口只需提交文本和语言、返回译文及 provider 元数据；Google Translate、DeepL、OpenAI-compatible 实现可替换。密钥走凭据存储，失败保留原文并展示可重试原因。翻译结果发布前仍须经过平台能力校验和用户确认。

## WebUI 与 CLI

WebUI 使用 Vue 3 + TypeScript，简约扁平布局和侧边栏；Topic 页面应能看见基础稿、各 Variant 的来源/状态、媒体预览、发布历史和外部关联。编辑保存采用明确的保存动作或可靠的本地自动保存，不把未确认的发布混入编辑。

CLI 覆盖同样的核心工作流，例如列出/创建 Topic、编辑或导入 Variant、预览、发布、重试、标记 URL 和导出备份。命令输出适合脚本处理，默认不输出凭据；交互确认是 CLI 发布桥接平台时的最后一道保护。

## 失败、重试与幂等

网络、鉴权、能力校验、媒体上传和平台限流要分类记录。只有明确可安全重试的错误才提供“重试”操作；鉴权失败先要求更新 Account。发布请求生成本地幂等键并记录远端结果，超时后重试前提示用户检查平台，避免重复发帖。浏览器桥接超时不能推断“未发布”，应保持 `needs_confirmation` 并允许用户用 URL 标记成功结果。

## 备份与恢复

提供导出 SQLite 数据、媒体文件和不含凭据的清单的备份命令；恢复前校验版本、校验值和迁移状态，避免覆盖当前数据。备份应能在本地离线完成。凭据单独重新配置，不把 token 混入普通备份。数据库迁移要可检测失败并保留原文件，发布历史是不可丢失的审计线索。

## 明确排除项

首版不做多人协作/组织/RBAC、云端部署与同步、时间线或关注内容抓取、全量历史导入、统计和粉丝分析、绕过平台访问限制、无人值守浏览器发布，以及为了“统一格式”而强制损失平台特性的转换。

## 关键决策记录

- **D1：URL 不触发后台抓取。** 反爬、登录和可见性差异使 URL 不能代表可读内容；URL 标记与用户主动快照分开，故障边界清楚。
- **D2：浏览器桥接只读取当前可见 DOM，发布默认人工确认。** 这让私密内容依赖用户已有权限，并把平台页面变化和最终发布风险留给用户确认。
- **D3：快照是本地事实，不是远端缓存。** 它支持跨平台复用和历史可追溯，同时不需要定时访问第三方。
- **D4：Variant 显式区分 linked 与 detached。** 从 BaseDraft 首次生成的是 linked 并记录 source revision；源稿变化只标记 outdated，用户确认应用更新后才更新版本。首次直接编辑自动转 detached，从其他 Variant 复制也默认 detached；绝不做实时同步或静默覆盖。
- **D5：单体 + 应用层复用。** 单用户本地项目不需要微服务，但 CLI/WebUI/适配器必须共享校验、状态和幂等逻辑。
- **D6：能力由 adapter 声明。** 平台差异先暴露给预览和用户，再逐步扩展实现，避免承诺所有站点都支持同样的格式。
